# ContextYield measurement and comparison contract

Status: implementation-accurate for v0.1, with a separate safe path for future physical studies. The Docker demo's quality, latency profile, and energy bounds are **synthetic configuration values**. `contextyield compare` reads synthetic full-information outcomes. Neither produces a measured-energy or carbon-savings result. See [architecture.md](architecture.md) for the execution path.

## What the current code knows

| Information | Current source and use | Honest interpretation |
| --- | --- | --- |
| Route quality, p95 latency, energy lower/upper bound | Operator-owned JSON registry; `choose()` checks constraints and ranks eligible targets by **upper energy bound**, then p95, priority, ID. | Forecast/profile metadata. Not the quality, latency, or energy observed for this request. Demo values are synthetic. |
| Evidence label | Registry value such as `profiled`/`benchmark_profile`, `synthetic`/`synthetic_demo`, or `unknown`/`unavailable`; optional profile expiry. | A declared provenance class, not independent validation of a profile. Expired evidence loses its usable energy upper bound. |
| Optional GPU observation | `energy.py` samples the local NVML cumulative-energy counter before and after the HTTP call and stores the delta in the attempt observation. | **Gross GPU-device-window joules** only. It includes idle and any concurrent GPU use; it excludes CPU, network, facility, and remote backend energy. |
| Fixture outcomes | `fixtures/synthetic-v1.json` supplies an outcome for each eligible action in the comparison. | Simulated quality, latency, and joules for a deterministic classroom comparison, not physical observations. |
| Unknown | Missing/expired bound, absent/unsupported/reset meter, or remote service without trustworthy data. | Unknown is not zero. A hard energy cap cannot be satisfied by an unknown upper bound. |

The caller can require profiled evidence, allow demo synthetic evidence, or allow unknown energy. `choose()` rejects a target without a valid upper bound when the caller sets an energy cap. With unknown allowed and no cap, a known-bound route ranks ahead of an unknown-bound route; if only unknown routes are eligible, the decision reason says so. These rules constrain **declared forecasts**. The live NVML observation is recorded after dispatch and does not update the current request's choice or automatically calibrate registry profiles.

`contextyield evaluate` is a separate, opt-in chat quality check. It sends 10 to 1000 labeled requests directly to one registered backend, scores a case-insensitive expected substring, and reports accuracy, failed-sample count, and p95 latency across all attempts with a fixture hash. Individual HTTP, timeout, transport, and invalid-response failures count as incorrect; any such failure suppresses suggested route fields. It stores neither prompts nor responses, but its sample IDs appear in the report. Its result-derived `quality_eval_id` includes each case's correctness and error code, so a score change cannot reuse an ID merely because the fixture is unchanged. This score is useful to exercise an evaluation pipeline; it cannot establish safety, factual accuracy, retrieval quality, or a statistically justified production floor by itself. It does not measure energy. The echo fixture is a command demonstration, not a benchmark.

In the production loader, `synthetic` and `synthetic_demo` route labels are rejected and the API rejects a request asking for `allow_synthetic_demo`. Positive quality claims need an evaluation ID; profiled routes need expiry, profile ID, evaluation ID, and a hardware fingerprint matching the deployment setting. These checks validate declarations, **not** the trustworthiness or transferability of an externally supplied profile.

## Evidence taxonomy for reports

Use distinct terms even when values share the unit “joules”:

1. **Observed aggregate/device window:** a valid counter delta for a named local GPU and interval. NVML's total-energy query is reported in millijoules since driver reload on supported devices [NVIDIA NVML API](https://docs.nvidia.com/deploy/archive/R535/nvml-api/group__nvmlDeviceQueries.html). ContextYield currently converts the before/after delta to joules. It does not measure system or facility energy.
2. **Attributed request estimate:** a documented allocation of aggregate energy, with idle and concurrency assumptions and an uncertainty interval. **Not implemented.** The current `exclusive_device` flag merely lets an operator attest exclusivity and sets an `attributable_to_request` boolean; the code does not verify exclusivity or subtract idle. Even with that flag, the number remains gross device-window energy, not incremental request energy.
3. **Profile forecast:** a route interval derived from measured runs on a comparable hardware/workload envelope. The optional `contextyield profile` command gathers at least ten exclusive NVML device-window samples and emits empirical min/max, p95 latency, and an exact-substring quality score. It does **not** fit a predictive model, calculate a statistical coverage interval, subtract idle energy, perform held-out validation, or detect drift. Using its output as a production forecast requires an operator's independent validation.
4. **Synthetic/proxy:** seeded fixture joules, token/time proxies, pricing, and demo registry bounds. Never label them measured.
5. **Unknown:** absent or incompatible evidence. Preserve this class in receipts and reports.

A failed or unsupported NVML read yields an unavailable observation rather than zero. A decreasing counter is treated as reset/unavailable. The probe does not record a device UUID, continuous time series, shared-load detector, or uncertainty interval, so a single successful delta should not be reported with unwarranted precision. For a hosted model or remote tool, a counter on the gateway machine would observe the gateway GPU, **not** the remote service; such a reading must not be presented as the backend's energy. The CPU-only Compose demo does not install/use the optional NVML dependency or a physical meter.

For an `exclusive_device=true` route, the gateway allows one in-flight request on that target and acquires an in-process lock shared by routes configured with the same meter. This prevents overlap **inside one gateway process**, but does not detect jobs outside ContextYield or coordinate other replicas. Operators must isolate the GPU or provide an external global lease before treating a device-window delta as request-attributable.

## Current comparison: what is and is not reproducible

`contextyield compare --fixture fixtures/synthetic-v1.json --out ...` evaluates each task against the static registry. It calls the same pure `choose()` for the energy policy, then chooses the fastest eligible target and the lowest-priority-number eligible target as two alternatives. The fixture must provide an outcome for every selected action. The report contains completed/rejected counts, mean fixture quality, p95 fixture latency, and total **synthetic** joules by policy. The JSON manifest hashes the fixture and registry and labels the evidence `synthetic_full_information_fixture`; the report includes a warning.

This is a deterministic *choice/outcome table* for a fixed fixture and registry, not a request-arrival trace. It does **not** run HTTP backends, sample NVML, use a virtual clock, model queue wait, apply the eight live slots or circuit breaker, simulate retries, compute fairness, or estimate production counterfactuals. Its manifest does not cryptographically pin all code/dependencies or hardware. Rerun the same checked-out version and inputs to compare output, but do not treat the report as proof of real-world gains.

For any published comparison, show the baseline and explicit quality/latency constraints. Do not write “X% measured energy saved” from the fixture, declared route bounds, or gateway-side measurement of a remote backend. A lower synthetic total is only a property of the fixture.

## Safe physical measurement and calibration path

1. Define the measurand first: GPU-device-window, CPU package, server input, or facility electricity. Record hardware, driver, model/backend version, workload, concurrency, clock source, and whether idle is included. Keep boundaries comparable across policies.
2. Opt in to a supported **read-only** meter. Check actual device/counter availability, unit, reset behavior, and permissions. The current adapter reads local NVML; [DCGM exporter](https://docs.nvidia.com/datacenter/dcgm/latest/reference/dcgm-exporter-metrics.html) is a possible future telemetry source, **not an implemented ContextYield adapter**. Do not change clocks, power limits, fans, firmware, or security settings for a demo.
3. Measure idle and isolated-load windows, then mixed-concurrency windows; repeat and randomize run order. Compare the counter delta with elapsed time and trace gaps/resets. For incremental energy, subtract a separately estimated idle contribution and propagate its uncertainty. Under overlap, per-request allocation is a model, not direct measurement.
4. Run the optional `contextyield profile` command only on an isolated, co-located NVIDIA inference route with a private benchmark fixture. It records a hardware fingerprint, sample count, empirical gross device-energy range, p95 latency, and exact-substring benchmark score without retaining prompts in its output. This is a **starting profile**, not a calibrated guarantee. Validate on held-out runs, record error and the model/load envelope, and do not reuse on a different GPU, driver, model, or batching configuration. The current registry checks expiry and deployment hardware fingerprint but cannot detect workload drift or validate fit quality itself.
5. Distinguish sensor uncertainty, run-to-run variance, attribution uncertainty, and statistical confidence. State the interval method and assumptions; NIST's [uncertainty overview](https://physics.nist.gov/cuu/Uncertainty/) and [expanded-uncertainty definition](https://www.nist.gov/glossary-term/23121) are useful anchors. No current ContextYield report computes such intervals.

A future controlled policy study would use matched traffic, repeated randomized order, quality and p95 guardrails, and measured aggregate energy at the same boundary. A future online A/B test would need stable assignment, capacity isolation or interference analysis, and confidence intervals; it is not implemented here. Production shadow choices cannot reveal unchosen-action outcomes, and off-policy estimates can be high-variance without action overlap [primary logged-bandit study](https://arxiv.org/abs/1703.06180). No carbon calculation or grid-intensity integration is implemented.

## Checks before making a physical-energy claim

Confirm supported local hardware and the meter boundary; verify exclusive-use claims independently; validate counter resets and background load; run repeated baseline/candidate trials with comparable quality and latency; retain raw aggregate traces and calibration provenance; report unknown coverage and uncertainty. If any of these is missing, report a proxy, forecast, or unknown—not measured savings.
