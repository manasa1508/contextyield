# ContextYield threat model

Status: implementation-accurate v0.2 risk assessment, **not** a security certification. The local Compose stack is bound to loopback with demo credentials and is not an internet-facing deployment template. This document distinguishes controls in code from controls an operator still must add. See [architecture.md](architecture.md) for request/receipt semantics, [repo-and-task-integration.md](repo-and-task-integration.md) for task telemetry, and [measurement.md](measurement.md) for evidence limits.

## Assets and trust boundaries

Assets are tenant prompts and tool inputs/outputs in transit, private evaluation fixtures, gateway/upstream/database credentials, static route configuration, per-tenant receipts and request hashes, synthetic comparison artifacts, backend capacity, and optional GPU counter observations. Client content, model output, tool output, fixtures, and route destinations controlled by an untrusted operator or compromised configuration must be treated as data, not instructions.

```text
client ── Bearer key ──> FastAPI validation/tenant mapping ──> configured target
                               │                               (one HTTP POST)
                               └── receipt/attempt ──> PostgreSQL

operator-owned JSON/env ──> registry, tenant keys, backend secrets
optional local NVML access ──> gross GPU-device-window observation
synthetic fixture JSON ──> offline compare CLI (no backend call)
private quality fixture ──> opt-in evaluate CLI ──> registered chat backend
```

The API key maps to a tenant and `GET /v1/receipts/{id}` queries by both tenant and receipt ID. It is **not** a route allowlist: any authenticated tenant can request any registered matching capability. The receipt row stores a keyed HMAC-SHA-256 of canonical request content for idempotency and the constraints/candidate decision snapshot, but not raw messages, tool input, output, or upstream secret. Keep `CY_HASH_KEY` separate from the database and stable across replicas/rotation; if it leaks, predictable requests may still be guessed. This is not anonymization. PostgreSQL administrators can alter records; application-level immutable decision JSON is not a cryptographic audit guarantee.

## Current controls versus gaps

| Risk | Implemented control | Residual risk / required addition |
| --- | --- | --- |
| Unauthorized access or cross-tenant receipt read | Bearer API key from `CY_API_KEYS_JSON`; constant-time key comparison; tenant-scoped receipt query. Request models forbid extra fields and limit message/input size; middleware caps body at 64 KiB. | Static keys have no rotation flow or granular roles. No per-tenant route allowlist or distributed rate limit. Add ingress identity, key rotation, tenant authorization, abuse limits, and cross-tenant tests. OWASP highlights object authorization and authentication risks [OWASP API Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/). |
| SSRF or unexpected egress | Clients cannot supply a URL; registry is loaded from operator-owned JSON. Production mode requires HTTPS route URLs and rejects embedded URL usernames. | No DNS/IP pinning, runtime egress allowlist, or private-address/metadata protection is implemented. A bad registry or compromised DNS can still redirect traffic at network level. Deploy with network egress policy and review destinations; test resolution/redirect behavior. |
| Mutating or dangerous tool execution | Tool route must declare `read_only=true`; tool calls are explicit and model-emitted tool-call text is not executed. Input is a bounded string map. | The declaration is not backed by a sandbox, scope inspection, or backend permission test. Use backend read-only credentials and a narrow capability contract; do not register shell, general browser, arbitrary SQL, or write-capable endpoints. “Read-only” may still consume quota or reveal data. |
| Prompt injection and malicious upstream output | Gateway does not interpret upstream output as a policy/config change. Chat and embedding routes check the expected response shape; tool routes require a JSON object. | These checks do not prove that content is safe or accurate. Caller-side agents must treat model/tool output as untrusted. Add capability-specific tool validation and downstream prompt-injection defenses where needed. |
| Secret or content exposure | Upstream bearer/basic secrets are looked up from environment; raw request/output are omitted from receipt rows; `/metrics` requires a gateway key. | Demo key/database credentials are insecure by design; exceptions, ingress, upstreams, logs, and backups still need review. `/docs` and health endpoints are not protected by the gateway API key. Add ingress TLS, secret manager/rotation, log redaction, and retention/deletion policy. |
| Task event abuse or misleading provenance | Strict metadata-only schema rejects arbitrary prompt/output fields; writes and summaries are tenant-scoped, bounded at 64 KiB per request and 1,000 events per summary; event IDs are idempotent. | Event labels, claimed quality, cost, and energy are caller-supplied and not cryptographically verified. No retention job, tenant quota, or event signing exists. Add authenticated ingestion limits and independent provenance before using these fields for billing or policy enforcement. |
| Local source scan and MCP facade | Scanner is read-only, skips symlinks and large/generated files, and returns location/category metadata. The stdio facade uses one operator-approved root and exposes no arbitrary path argument. | File names and framework choices may still be sensitive; do not point `CY_SCAN_ROOT` at an unapproved tree. The local MCP facade is not an organization-wide OAuth gateway and inherits the host process's file permissions. |
| Resource exhaustion | Requests over 64 KiB are rejected, with field limits, per-route timeout, eight non-blocking slots per target per process, and a local three-failure/30-second circuit. | The current middleware buffers a request before checking its actual size when `Content-Length` is absent or false; the 64 KiB rejection is **not** an ingress memory bound. No tenant rate limit, fair queue, global slot limit, or distributed circuit exists. Add an ingress body limit and distributed controls before public exposure. |
| Duplicate/ambiguous backend call | Decision committed before dispatch; same tenant/key/request returns 409 with receipt (no redispatch); changed body under key returns 422. Timeouts are not automatically retried. Reconciliation marks old pending receipts unknown. | No cached result, exactly-once guarantee, or certainty after a lost response. A caller that retries without the same key can cause another call. Read-only upstreams can still incur billing and load. |
| Receipt/evidence integrity | PostgreSQL transaction inserts decision before call; terminal outcome and one attempt are written together. Profile and registry IDs appear in decision; meter reset/unavailability produces unavailable observation. | Receipt is a mutable DB row with application-immutable decision JSON, not append-only events or a signed transparency log. Profiles are operator declarations, and `exclusive_device` is an unverified assertion. Protect DB access/backups and avoid overstating measurement. |
| Comparison artifact abuse | Offline CLI reads JSON fixture and does not contact upstreams. Manifest includes fixture/registry hashes. | No sandbox for untrusted fixtures, comprehensive size/schema limits, or complete build provenance. Run replay without production secrets and add parser bounds/provenance checks before accepting third-party fixtures. |
| Evaluation data leakage or unexpected charges | `evaluate` requires `--confirm-live-requests`, limits the private fixture to 2 MB and 10..1000 cases, and stores only sample IDs, correctness, latency, and hashes. | It sends full prompts to the registered backend and may incur charges. Sample IDs and shell history can still carry private data. Keep fixtures and reports private, use non-sensitive IDs, and apply provider-side budgets. The score is not a general quality or energy certificate. |

## Failure surfaces worth testing

A missing upstream secret or unexpected adapter exception after decision insert may leave a pending receipt; the reconciliation CLI can later mark it `unknown`. A database failure before decision insertion stops dispatch, while a failure after a completed upstream call can cause a 503 and an unresolved pending receipt. These are not exactly-once semantics. Upstream timeout/transport failures are ambiguous; the gateway returns a failure without retrying. The circuit and eight-slot bulkhead are local to each process and reset on process restart. These behaviors need process-kill, DB-outage, upstream-timeout, and multi-process tests before production use.

Prometheus request counters and upstream-latency histogram are available, but there is **no OpenTelemetry tracing** or built-in alerting. Readiness checks PostgreSQL only, not upstream health. Production operations must supply ingress TLS, PostgreSQL transport/security and backups, restore drills, secret rotation, dependency/image scanning, network egress policy, distributed rate limiting, monitoring and alerting, retention rules, and hardening tests. Do not rely solely on a serving backend's own API key: [vLLM documents endpoints outside its API-key protection](https://github.com/vllm-project/vllm/blob/main/docs/serving/online_serving/openai_compatible_server.md). PostgreSQL durability depends on storage and WAL/fsync configuration [PostgreSQL reliability guidance](https://www.postgresql.org/docs/current/wal-reliability.html).

The principal residual risks are false read-only assurance, cross-tenant capability access, bad or malicious registry destinations, resource exhaustion across replicas, ambiguous backend effects, and misleading energy claims. The controls listed as additions are **future work**, not features silently supplied by `CY_MODE=production`.
