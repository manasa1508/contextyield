# ContextYield research notes and decision record

As of 2026-10-09. These notes connect the **implemented v0.1 reference** to primary sources and identify work it does not yet do. They are not a systematic prior-art review, a novelty claim, or proof of production readiness. See [architecture.md](architecture.md), [measurement.md](measurement.md), and [threat-model.md](threat-model.md) for the operational contract.

## Position relative to existing work

Energy-aware routing is not ContextYield's invention. [GreenServ](https://arxiv.org/abs/2601.17551) studies context-aware adaptive multi-model routing with accuracy/energy trade-offs. [Measured Joules, Learned Routes](https://arxiv.org/abs/2609.23085) profiles correctness, latency, power, and GPU energy to learn a router. [Routing LLM Inference to the Cleanest Grid in Real Time](https://arxiv.org/abs/2608.06188) reports live grid-aware placement using a pressure-based baseline and telemetry-based request attribution. These results cannot be transferred to ContextYield's demo profiles or fixtures, and “routes by energy” is not a defensible novelty statement.

[vLLM's OpenAI-compatible server](https://github.com/vllm-project/vllm/blob/main/docs/serving/online_serving/openai_compatible_server.md) is one possible registered inference backend; its [production stack](https://github.com/vllm-project/vllm/blob/main/docs/deployment/integrations/production-stack.md) already addresses serving/deployment concerns. ContextYield is a gateway/reference, not a serving engine. Its distinct educational emphasis is explicit route constraints, one committed decision receipt, evidence labels, and a reproducible *synthetic* policy table. Whether the combination is novel research remains unassessed.

## Implemented design decisions

| Decision in code | Rationale and exact limit | Alternative / future trigger |
| --- | --- | --- |
| FastAPI synchronous `/v1/execute` plus PostgreSQL | Small request path; commit decision before one upstream call, then commit attempt and terminal outcome. This is a receipt row, **not** an append-only event architecture. | A richer event log only if audit/query needs justify it. Keep crash ambiguity explicit. PostgreSQL durability depends on configuration [PostgreSQL WAL](https://www.postgresql.org/docs/current/wal-intro.html). |
| Pure `choose()` over static JSON targets | Deterministic hard filters and ranking by usable energy upper bound, p95, priority, ID; candidate reasons are inspectable. | Queue-aware or learned policies require validated runtime/quality data and new experiments. Static quality/p95 numbers are operator claims until benchmarked. |
| Eight local slots and three-failure/30-second circuit per target | Simple bulkhead and failure isolation; immediate 429 when selected route is full. No application-level admission queue, fairness, global limit, or post-selection fallback. | Shared leases, fair queue, distributed rate control, and replay of contention if multi-replica or latency requirements justify them. |
| Static registry + JSON tenant keys | Fixed destinations avoid caller-provided URL routing; receipt lookup is tenant-scoped. Tool `read_only` is a config attestation. | Granular tenant route allowlists, identity provider, secret rotation, backend permission enforcement, and egress policy for production. |
| Optional local NVML counter window and `contextyield profile` CLI | On supported co-located NVIDIA devices the request path can store a gross device-window delta. The opt-in CLI can summarize at least ten operator-attested exclusive windows, benchmark exact-substring quality, and emit a hardware-fingerprinted empirical profile. | Held-out validation, idle subtraction, concurrency attribution, uncertainty coverage, drift checks, and controlled policy trials before savings claims. [NVIDIA NVML API](https://docs.nvidia.com/deploy/archive/R535/nvml-api/group__nvmlDeviceQueries.html) defines the counter's units and support limits. |
| Full-information synthetic fixture compare | Same task fixture evaluates energy/fastest/priority choices and emits manifest hashes plus report. No upstream call, virtual clock, arrivals, queue, or physical meter. | Controlled physical trials and online evaluation once infrastructure and consent permit them. |
| Prometheus metrics | Requests/outcomes and upstream-call latency are visible through authenticated `/metrics`. | OpenTelemetry tracing, alerts, and richer per-tenant operations are future work. |

The receipt boundary intentionally favors auditability over uninterrupted availability: if PostgreSQL cannot insert the decision, the request does not dispatch. A lost terminal update can leave a pending receipt; `contextyield reconcile` marks old pending rows `unknown` without reissuing a call. Reusing an idempotency key returns the original receipt ID with 409 (or 422 for different content), **not** a cached response. This avoids an unsupported exactly-once claim.

## Evidence and comparison guardrails

| Primary source | Supports | Does not establish for ContextYield |
| --- | --- | --- |
| [NVIDIA NVML energy counter](https://docs.nvidia.com/deploy/archive/R535/nvml-api/group__nvmlDeviceQueries.html) | Supported GPUs can expose cumulative local GPU energy in millijoules since driver reload. | A remote backend's energy, total facility energy, automatic per-request attribution, or the demo's synthetic joules. |
| [NVIDIA DCGM exporter metrics](https://docs.nvidia.com/datacenter/dcgm/latest/reference/dcgm-exporter-metrics.html) | Another possible GPU telemetry source with conditional field availability. | A DCGM adapter in current ContextYield; current code uses optional local NVML only. |
| [NIST uncertainty guidance](https://physics.nist.gov/cuu/Uncertainty/) | Measurement needs stated scope and uncertainty method. | Validated uncertainty intervals from the current fixture report or one NVML delta. |
| [PostgreSQL non-durable settings](https://www.postgresql.org/docs/current/non-durability.html) | Weakening WAL/fsync/commit settings changes receipt durability. | Exactly-once effects at an external HTTP backend. |
| [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) | Tenant authorization, resource limits, and SSRF need design attention. | Security certification from merely using fixed URLs and API keys. |
| [Logged-bandit evaluation study](https://arxiv.org/abs/1703.06180) | Off-policy estimates can have high variance when logging and target policies diverge. | Counterfactual outcomes for unchosen routes in the current fixture or live receipt. |

The current `comparison.json` and `report.md` report fixture quality, latency, and **synthetic** joules. They do not measure energy, queue behavior, real user quality, or causal production gains. The manifest hashes fixture and registry bytes and includes a version label; it does not pin every dependency or code revision. A production-quality comparison would predeclare quality/latency guardrails, measure the same physical boundary on matched repeated workloads, account for concurrency and unknown coverage, and report uncertainty. Until then, the correct claim is that ContextYield demonstrates policy behavior under stated synthetic inputs.

Open questions for the next design iteration: Can route quality/p95/profile bounds be validated on target workloads? Is the NVML counter available on the actual backend host, and can device use be isolated? What tenant authorization policy is required? What happens to capacity and circuit state with multiple workers/replicas? Which measured workload and uncertainty method would justify an energy-impact claim? Answer those with evidence before expanding the README or public claims.
